# CrabLogic (папка CrabLogic) — визуальное программирование микроконтроллеров на Rust

Своя программа визуального программирования микроконтроллеров (FBD),
написанная с нуля на Rust, со встроенным ИИ-помощником и MCP-сервером.

Полная архитектура и решения: `Архитектура и план.md` в корне.
Перед крупными изменениями сверяйся с ним; если решение меняется — обнови и его.

## Общение и стиль

- Общаемся на русском. Интерфейс программы, сообщения об ошибках и описания блоков — на русском.
- Идентификаторы в коде, имена крейтов и комментарии к коду — на английском.
- Программа пока для одного пользователя: без установщиков и лишней полировки, но код чистый.
- Раскладку и функциональность держим привычными для FBD-сред; код, иконки и графику делаем свои.

## Оформление левой панели (дерево проекта)

Один вид для всех элементов дерева (теги, радио, Modbus, сеть, MQTT, дисплеи):

- **Группа** (Входы, Выходы, Публикации, Slave…): складывающийся заголовок, сразу после названия — маленькая кнопка «+»
  (`panels::add_group`). Внутри — строки группы. Кнопки «+» без названия, значков настроек и корзины в строках нет.
- **Строка элемента** — плоская, как у переменной (`panels::drag_row`): название слева, текст **цвета связей своего типа**
  (bool, int, float, строка — `canvas::signal_color`; без типа — обычный цвет текста). Если блок ещё не стоит на листе,
  справа **оранжевый `[✕]`** (цвет предупреждения темы; он же у переменной, которая нигде не используется). Метки «стоит на листе» (стрелки) нет, метку перед названием не ставим. Рисует `panels::row_label`.
- **Действия строки:** перетаскивание на лист (весь блок), щелчок — найти на листе, двойной щелчок — настройки,
  правый щелчок — меню: «Найти на плате», «Свойства…», «Удалить из проекта».
- **Сервис** (Wi-Fi, Ethernet, веб-интерфейс, MQTT): такая же плоская строка (не раскрывающийся список); справа от названия —
  переключатель вкл/выкл (`dialogs::toggle_switch`, не галочка); в меню — «Настройки…», «Включить», «Блок целиком удалить».
  Вложенные списки (публикации, подписки, страницы) стоят под строкой с отступом.
- Удаление с листа: теги, сервисы и радио (модем, slave, master) остаются в дереве с меткой `[✕]`, из проекта их убирает только «Удалить из проекта»; дисплей удаляется целиком.
- Новый элемент дерева делаем по этому образцу, не придумывая свой вид; текст интерфейса — через `i18n::tr`.

## Окружение

- Windows 10/11 x64, 16 ГБ ОЗУ, SSD. Rust — toolchain MSVC (stable).
- Прошивка: готовый мастер на Rust (`firmware/master-rs`, образы в `firmware/<чип>/`), заливка через espflash; схема едет на плату модулями WASM. `arduino-cli` и C++ удалены (13.11.2026). Если чего-то нет — подскажи, как установить, и не ломай остальное.
- Целевая плата первой версии: ESP32 (DevKit), заливка и отладка по USB.

## Ключевые решения (кратко)

- GUI: egui (eframe). Прошивка — мастер на Rust, схема — модули WASM по листам (`crab-codegen`); путь через скетч Arduino C++ и arduino-cli удалён 13.11.2026.
- Проект = один файл `<имя>.crab` — ZIP-архив с `project.toml` (плата, настройки), `logic.toml` (блоки и связи), `layout.toml` (координаты, только для редактора) и `boards.pdf` (картинка всех плат, пересоздаётся при сохранении). Логика отдельно от координат. Старый формат (папка с теми же TOML) читается; примеры в `examples/` хранятся папками ради git.
- Блоки с понятными id (`pressure`, `pump`); связи `from = "блок.порт"`, `to = "блок.порт"`. TOML на диске, JSON для ИИ — одни serde-структуры.
- Блоки расширяются файлами без перекомпиляции: `library/<block>/block.toml` + `docs.md` (+ `block.wasm` у блоков пользователя и драйверов); встроенные блоки — Rust в `crab-blocks`. Блок на C++ не поддерживается; горячая подгрузка. Составные блоки — позже.
- Заливка модулей без перепрошивки мастера; AOT-компиляция модулей (`wamrc`) в фоне.
- Онлайн-отладка по USB: модуль в прошивке, двоичные кадры с CRC, отпечаток схемы, уставки на лету, форсировка. Транспорт — отдельный слой (Wi-Fi позже).
- ИИ: один общий набор команд (прочитать схему, добавить блок, соединить, проверить, собрать/прошить, читать живые значения, создать блок). Его вызывают и чат в редакторе, и MCP-сервер. Провайдеры через общий трейт, Claude по умолчанию.

## Предлагаемая структура (cargo workspace)

```
crates/
  crab-core/     модель проекта, загрузка/сохранение TOML, библиотека блоков, проверка схемы, порядок выполнения
  crab-codegen/  сборка листов схемы в модули WASM, проверка блоков
  crab-build/    заливка мастера (espflash) и модулей на плату, порты, AOT
  crab-pdf/      картинка всех плат проекта в PDF (кладётся в архив проекта)
  crab-cli/      командная строка: check / gen-wasm / flash-master / monitor / convert / block / board
  (позже) crab-debug, crab-ai, crab-mcp, crab-web, crab-editor
library/        блоки-файлы
examples/       примеры проектов (начать с насоса из плана)
```

Структуру можно уточнять, но держи границы: ядро не знает про GUI, ИИ и инструменты прошивки.

## План работ

1. **Ядро** ← начинаем здесь. Готово, когда `crablogic check examples/pump` находит ошибки схемы
   (несуществующий блок/порт, несовместимые типы, вход без источника, циклы без памяти),
   `crablogic gen-wasm` собирает модули листов, `crablogic flash-master` и `gen-wasm --upload` заливают мастер и модули на плату. (Исторически: первая версия шла через скетч и arduino-cli, удалено 13.11.2026.)
2. **Базовые блоки**: входы/выходы (цифр., АЦП, ШИМ), DS18B20, DHT22, И/ИЛИ/НЕ/XOR, RS-триггер, фронты,
   TON/TOF, импульс, генератор, сравнение, арифметика, масштабирование, гистерезис, счётчик, сохранение во флеш.
3. **Редактор** на egui: привычная раскладка (сверху меню и инструменты, слева дерево и теги,
   справа библиотека и вкладка ИИ, в центре платы-листы).
4. **Онлайн-отладка** по USB.
5. **ИИ-чат и MCP-сервер**.

## Правила работы

- Код, который выполняется на микроконтроллере (модули листа, драйверы `block.wasm`, мастер), прежде всего
  оптимален по скорости, ОЗУ и флешу: без решений, избыточных для задачи. Пример: не `f64` везде, а целые по
  умолчанию, `f32` только для портов и переменных `float`, `f64` не используется (`specs/no-f64`). Так же — без
  лишних копий, аллокаций, буферов «с запасом» и универсальных обёрток там, где хватает простого кода.
- Программа идёт не только в DIY, но и в промышленность: код на плате пишем по правилам промышленной
  надёжности (по духу IEC 61131-3 и IEC 61508, без заявлений о сертификации). Детерминированный скан
  (входы → логика → выходы, период по сетке), без аллокаций и блокирующих ожиданий в пути шага, ограниченные
  буферы и очереди, любой отказ (ошибка модуля, переполнение, зависание, потеря связи) обнаруживается,
  считается и переводит выходы в заданное безопасное состояние, проверка всех внешних данных (команды,
  образы модулей, CRC), никаких паник в рабочем цикле. Функции аварийной защиты (аварийный стоп и т. п.) —
  только аппаратно, в справке об этом говорим прямо.
- Перед завершением шага: `cargo fmt`, `cargo clippy --all-targets`, `cargo test`.
- После больших правок (генератор модулей, интерфейсы, драйверы, мастер) — замер скорости и ОЗУ на платах
  (`crablogic bench`, ESP32 и C3, сравнение с прошлым отчётом) и строка в `bench/history.md`.
- На каждый блок — тест сборки модуля (`crab-codegen/tests/library_modules.rs`) и пример в `examples/`.
- Не удаляй файлы проекта без явной просьбы.
- Справка (`help/*.md`) всегда актуальна: меняешь поведение, формат проекта, интерфейс или блок — в том же шаге правь соответствующую страницу справки (и `docs.md` блока). Переводы `help/<язык>/` обновляй следом.

## Спецификации крупных задач (по мотивам Spec Kit)

Для маленьких правок и багов — сразу код. Для крупной фичи (новый блок-семейство, протокол,
режим сборки, правка формата проекта) — сначала короткая спецификация, потом код.
Spec Kit как инструмент не ставим, берём только порядок:

1. `specs/<фича>/spec.md` — **что и зачем**, без выбора технологий: цель, сценарии пользователя,
   критерии готовности (проверяемые), что вне задачи. Принципы проекта — это этот файл и
   файл архитектуры; спека им не противоречит.
2. Вопросы по неясным местам — пользователю (одним сообщением), ответы записать в спеку.
3. `specs/<фича>/plan.md` — **как**: затронутые крейты и файлы, формат данных, риски. Если решение
   меняет архитектуру — обновить файл архитектуры.
4. `specs/<фича>/tasks.md` — чек-лист задач по порядку, у каждой — как проверить (тест/пример/снимок).
5. Реализация по задачам; отмечать `[x]` по мере готовности.
6. Сверка в конце: пройти критерии из спеки и задачи, найденное недоделанное дописать в `tasks.md`
   и закрыть; в ответе пользователю — что из критериев выполнено, а что не проверено (например,
   не проверено на железе).

Спеку и план пишем кратко (по странице), на русском. Папку `specs/` коммитим вместе с кодом.

## Экономия контекста

- Во время работы проверяй только затронутый крейт: `cargo test -p <crate> -q`,
  `cargo clippy -p <crate> --all-targets`. Полный прогон по workspace — только в конце шага.
- Из длинного вывода команд показывай только ошибки и предупреждения
  (например, через `| tail` или `grep -E "error|warning"`).
- Не читай `target/`, `.crab/` и `Cargo.lock`; снимки (`.wat`) читай точечно, не целиком.
- Файл архитектуры читай по нужному разделу (сначала `grep` заголовков), а не целиком.
- Ищи код через `grep`/`Glob` по имени, а не чтением файлов подряд; большие файлы читай диапазонами строк.
- Субагенты: код по готовому заданию (файлы, сигнатуры, критерий готовности, тесты на ПК) можно
  отдавать субагентам Sonnet. За основной сессией остаются архитектура и интерфейсы, разбор diff,
  работа с платой (прошивка, COM-порт, FFI/`unsafe`), `tasks.md` и справка. Мелкие правки — без
  субагентов. Параллельно — только задания, не трогающие одни и те же файлы.
