# Внутренняя шина pub/sub и Sparkplug B

Продолжение `specs/wasm-on-mcu/`, `specs/wasm-io/`, `specs/debug-image/`. Три слоя, не знающие друг о друге:

1. **Внутренняя шина** (только внутри одной ESP32) — связь WASM-модулей между собой и с хостом.
2. **Образ состояния** (`specs/debug-image`) — наружу для отладки и веба: плоская структура + таблица смещений.
3. **Sparkplug B** — наружу для IoT-мира поверх MQTT. Внутренняя шина с MQTT не связана.

## Цель
Модуль (датчик, логика, телеграм-бот) не знает, где он работает и кто его соседи: он вызывает функции хоста и
публикует/читает топики. Любой модуль заменяется на лету, пока остальные продолжают работать.

## Сценарии
1. Меняем модуль датчика температуры (горячая перезагрузка): телеграм-бот не останавливается, после замены
   новый датчик публикует в тот же топик, бот читает как раньше. Новый/перезапущенный подписчик сразу получает
   последнее значение топика.
2. Переполнение очереди медленного подписчика не задерживает остальных и не ломает такт: поведение задано политикой,
   потери считаются и видны в отладке.
3. Платформа подключается к брокеру как Sparkplug-узел: в `NBIRTH`/`DBIRTH` уходят метрики из таблицы смещений
   образа, дальше `NDATA`/`DDATA` по изменению; при обрыве брокер публикует `NDEATH`.

## Критерии готовности
- Остаётся ABI v3: `publish`, `subscribe`, доставка `on_message` между шагами (уже есть в `crab-sim` и прототипе
  мастера `specs/wasm-on-mcu/proto/master`). Новый ABI не вводится; добавляются только поведение и лимиты ниже.
  Один и тот же модуль работает в `crab-sim`/браузере и на ESP32 без изменений.
- Топик имеет тип и максимальную длину сообщения, задаваемые при сборке; публикация длиннее — ошибка сборки/вызова.
- Два вида топиков: **состояние** (хранится последнее значение, подписчик читает его сразу) и **событие**
  (очередь FIFO у каждого подписчика, ограниченная; при переполнении выбрасывается самое старое, счётчик потерь растёт).
- Реализация на ESP32 — очереди на подписчика (сейчас кольцо из 4 сообщений, при переполнении новое молча
  теряется — меняем на явную политику); порядок доставки FIFO в пределах топика; `publish` не ждёт.
- Теги остаются как есть и могут читаться как топики-состояния (отдельный шаг, не ломает `crab-sim`).
- Замена модуля: подписки и последнее значение сохраняются хостом; тест «заменили публикатора — подписчик не
  перезапускался и увидел новое значение».
- Sparkplug B: метрики (имя, тип, алиас) строятся из карты смещений образа; `bdSeq`, `NBIRTH`, `DBIRTH`, `NDATA`,
  `DDATA`, `NDEATH` (как MQTT LWT); сборка protobuf-пейлоада проверяется тестом на эталонных байтах (совместимость
  с Eclipse Tahu). Параметры брокера, пароли и Wi-Fi лежат в модуле, а не в прошивке мастера.
- Справка и раздел архитектуры обновлены.

## Вне задачи
Шина между платами; перевод тегов и mqtt-блоков на шину; Sparkplug-команды (`NCMD`/`DCMD`) — вторым шагом;
перевод Arduino-вывода на общий IR (отдельная спека); C++ как промежуточный язык для схемы (схема эмитится в WASM
напрямую, C++ нужен только для пользовательских блоков).

## Состояние прототипа (07.11.2026)
Мастер: топик ≤ 23 байт, данные ≤ 64 байт, ≤ 4 подписки и очередь из 4 сообщений на модуль, совпадение по точному
имени, нет «последнего значения», нет счётчика потерь, переполнение — молча теряется новое сообщение.

## Ответы пользователя (07.11.2026)
1. Подписки только по точным именам (без масок) в первой версии.
2. Sparkplug только 3.0.
Размер очереди и максимум топиков — решаем в `plan.md` после замера ОЗУ.
