# Микроядро для WASM-модулей: общий Rust-хост для ПК и платы

Продолжение `specs/wasm-on-mcu/` (мастер-прошивка), `specs/pubsub-bus/` (шина) и `specs/mcu-memory/` (память мастера).
Исходное ТЗ — «Универсальный микроядерный WASM хост-рантайм для 32-битных МК с горячей заменой модулей»
(generational handles, SlotMap, аренда ресурсов с безопасным состоянием, pub/sub, квантование по fuel).

## Цель
Сейчас у модулей два хоста: `crab-sim` на ПК (Rust, wasmi) и мастер на плате (C++, wasm3). Правила дублируются,
ресурсы платы не привязаны к модулю: после сбоя или выгрузки модуля выход остаётся включённым, ШИМ работает
(`pinOnce` в мастере). Код модуля wasm3 держит в куче (≈ 3,2 × `.wasm`), на C3 с Wi-Fi + MQTT это предел ~15 КБ
на лист. Нужен один хост на Rust (`crab-kernel`), который:
- одинаково работает в симуляторе и на плате;
- отдаёт ресурсы модулю в аренду и при его остановке переводит их в безопасное состояние;
- выбирается по перспективе скорости и памяти, а не по наличию готовых библиотек (их можно переписать).

## Сценарии
1. Модуль управляет насосом и падает (trap, зависание) или его выгружают: выход насоса сразу уходит в безопасное
   состояние, ШИМ останавливается, подписки модуля снимаются; остальные модули работают.
2. Пользователь меняет модуль на лету: старый отдаёт ресурсы, новый их получает; ссылки на старый модуль
   (сообщения, события, таймеры) не доходят до нового.
3. Модуль с бесконечным циклом не вешает плату: по исчерпании кванта он приостанавливается и продолжает с того же
   места в следующем кванте; остальные модули получают своё время.
4. Схема и модули ведут себя одинаково в симуляторе на ПК и на плате (одно ядро, одни тесты).
5. На C3 с Wi-Fi + MQTT помещаются листы заметно крупнее нынешних ~15 КБ: код модуля во флеше, в ОЗУ только
   его память и стек.
6. Плата с Ethernet (W5500 по SPI или встроенный EMAC ESP32 с LAN8720) работает с Rust-мастером так же, как с C++.

## Критерии готовности
Этап «решение» (до Rust-мастера):
- Прототип WAMR (интерпретатор и AOT с XIP) на C3 по шаблону `proto/wasmi-c3`: для тех же модулей замерены шаг,
  загрузка/замена, ОЗУ, флеш (AOT ≈ 2–4 × `.wasm`, пересчёт областей `crabmod`), цена программной проверки границ
  памяти; цифры в `specs/wasm-on-mcu/plan.md` рядом с wasm3 и wasmi. По ним пользователь принимает решение о Rust-мастере.

Этап «ядро на ПК»:
- `crab-kernel` (no_std + alloc): поколенные ссылки на модули, таблица слотов, шина (правила `crab-sim::bus`),
  таблица аренды ресурсов с безопасным состоянием через `Drop`, жизненный цикл загрузка → квант → замена → выгрузка.
- Движок WASM спрятан за трейтом; на ПК — wasmi. `crab-sim` работает поверх ядра, все его тесты проходят.
- Тесты `cargo test`: ссылка на выгруженный модуль недействительна; после trap/выгрузки каждый арендованный
  ресурс в безопасном состоянии; бесконечный цикл приостанавливается и продолжается.
- Fuel не зависит от движка: эмиттер `crab-codegen` вставляет счётчик на обратных переходах циклов; снимок кода.

Этап «Rust-мастер» (если решение «да»):
- Мастер на Rust поверх ESP-IDF (`esp-idf-svc`) на C3 и ESP32: ядро + WAMR AOT; протокол USB совместим с нынешним
  (`put`, `list`, `info`, `tick`), редактор работает без изменений.
- Сеть: Wi-Fi, MQTT, Ethernet W5500 (SPI) и EMAC ESP32. На C3 с Wi-Fi + MQTT свободно не меньше, чем у C++-мастера
  (норма `mcu-memory` — 40 КБ), лист 30 КБ `.wasm` загружается.
- Справка (раздел про мастер и ограничения плат) обновлена.

## Вне задачи
- Битовый аллокатор: на ESP32 куча ESP-IDF уже TLSF, замеры не показали в нём узкого места.
- Свой форк wasmi с предтрансляцией во флеш: XIP даёт WAMR AOT.
- RP2040, STM32 и AVR: после ESP32 (решения «STM32 после ESP32», «AVR отложены»); ядро для них не закрывает дорогу.
- Перевод программных протоколов (OneWire, DHT) на RMT — отдельная задача драйверов.

## Решения (08.11.2026, ответы пользователя через родительскую сессию)
1. Хост и ядро — Rust (`crab-kernel`), один код на ПК и на плате. Аренда и безопасное состояние — через `Drop`.
   Движок WASM — за трейтом.
2. Движок на плате — WAMR AOT с XIP; `wamrc` (LLVM, есть Xtensa и riscv32) вызывает редактор при сборке модуля.
   wasmi остаётся движком ПК и симулятора.
3. Fuel — счётчик от эмиттера, а не движка; приостановка с продолжением работает и в AOT.
4. Rust-мастер — поверх ESP-IDF (`esp-idf-svc`), не bare-metal `esp-hal`: Wi-Fi, MQTT, W5500, EMAC; у WAMR есть порт
   под ESP-IDF.
5. Первым шагом — прототип WAMR на C3; решение о Rust-мастере — по его замерам.
6. Вторая платформа после ESP32 — как решено раньше, задачи 5b–8 не сдвигаются.
7. «Без ногодрыга»: простой `gpio_write` для реле и ламп остаётся; запрещены программные протоколы с точными
   таймингами — их со временем на RMT.
8. Зависший модуль в нынешнем C++-мастере — как сейчас, «остановить и перезапустить»; приостановка — в ядре.

9. Аренда в C++-мастере — упрощённая версия сейчас: при trap или выгрузке модуля его выходы уходят в безопасное
   состояние. Полная аренда (пины, ШИМ, подписки за модулем) — в Rust-мастере через `Drop`.
10. Безопасное состояние по умолчанию — выход 0, ШИМ стоп, вход без подтяжки. Блоки выходов получают параметр
    «при аварии: 0 / 1 / держать».
11. `wamrc` не кладём в поставку: редактор скачивает его при первой сборке AOT-модуля и кэширует; путь можно задать
    вручную в настройках инструментов.
12. Rust-мастер начинаем с C3 (обычный тулчейн), ESP32 через `espup` — следом.
13. ABI v4 со счётчиком fuel принят; старые модули пересобираются (понятный отказ при загрузке).

Ускорение шага AOT (там же, «Ускорение шага AOT»): флаги wamrc не помогают; обёртка-функция на каждый импорт

быстрее wasm3), но замедляет interp на 25–30 %; raw-нативы на хосте — ещё 6–12 %. Предлагается отдельной задачей
этапа 3 (правка эмиттера — после согласования).

## Решение по режиму исполнения листа (09.11.2026, ответ пользователя через родительскую сессию)
14. Режим (AOT или интерпретатор) выбирается на каждый лист; в одном мастере могут быть листы обоих режимов.
    В интерфейсе слов AOT и «интерпретатор» нет — свойство листа «Скорость»:
    - **Быстрый** — всегда AOT; не помещается во флеш — ошибка с подсказкой.
    - **Обычный** (по умолчанию) — AOT, если есть место, иначе без ускорения с предупреждением.
    - **Фоновый** — интерпретатор, экономит флеш; при нехватке места переводится первым. Позже, с приоритетами
      задач, фоновый лист получает и низкий приоритет.
15. При нехватке флеша редактор сам выбирает, кого перевести без ускорения: сначала фоновые, потом обычные
    с самым длинным периодом и лёгким шагом. Быстрые не трогает.
16. Перед заливкой — одно предупреждение на всю заливку: что случилось (лист, нужно/свободно), чем грозит (оценка
    шага до и после; не укладывается в период листа — «таймеры и импульсы будут неточными»), как исправить (удалить
    модули с платы, разделить лист, скачать wamrc). Кнопки «Залить так» / «Отмена», галочка «Больше не спрашивать
    для этого листа» (ставит «Фоновый»). Жёлтое предупреждение и в панели проверки по фоновой сборке.
17. В окне состояния платы у листа — «ускорен» / «без ускорения». CLI: предупреждение, флаг `--require-aot`
    делает его ошибкой. AOT и интерпретатор упоминаются только в справке.
18. Эмиттер при сборке под AOT выводит обёртку-функцию на каждый импорт, хост регистрирует raw-нативы
    (замеры «Ускорение шага AOT»). Код этапа 3 — после согласования.
