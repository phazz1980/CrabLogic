# План: аудит надёжности

## 1. Сторож шага — на таймере цикла, а не на TWDT

TWDT ESP-IDF один на всех: его время общее с проверкой задач простоя ядра 0, и время 200 мс сбросило бы
плату при долгой записи флеша или занятом Wi-Fi ядре 0. Поэтому сторож свой, на аппаратном таймере цикла
(`board/tick.rs`, GPTimer, прерывание в IRAM на ядре шага):

- `board/watchdog.rs`: срок `DEADLINE_US: AtomicU64`. Цикл перед каждым шагом ставит срок
  `now + max(100 периодов, 200 мс)`; на известные долгие работы между шагами (запуск модуля, запись образа)
  — `watchdog::hold(5 с)`.
- Прерывание метки сравнивает `esp_timer_get_time()` со сроком. Просрочено → выводы в безопасное состояние
  (таблица ниже) → запись причины в RTC-память (`.rtc_noinit`) → `esp_system_abort("scan watchdog")`:
  ESP-IDF пишет дамп и перезагружает плату. Если зависание с запрещёнными прерываниями — ловит штатный
  сторож прерываний ESP-IDF (INT_WDT, 300 мс).
- Перезагрузка считается сбойной (как паника) → после 3 подряд безопасный режим (уже есть).
- `info`: `reset=panic trip=scan` — причина из RTC-памяти, одна загрузка.
- Без аппаратного таймера (запасной цикл по тикам) — TWDT для потока шага с запасом 5 с и запись в журнал.

## 2. Безопасное состояние без мастера

`board/devices.rs` уже знает выводы модулей и их «при аварии». Для прерывания сторожа — копия в статической
таблице атомиков `SAFE: [AtomicU8; 49]` (вывод → нет / 0 / 1 / держать), заполняется при захвате вывода
выходом и чистится при освобождении. В прерывании: `esp_rom_gpio_connect_out_signal(pin, SIG_GPIO_OUT_IDX)`
(отвязать ШИМ) и запись уровня через регистр — функции ROM/IRAM. Состояние держится до сброса чипа
(ESP-IDF пишет дамп ~0,2 с), после сброса выводы — входы без подтяжки (справка).

## 3. Нехватка памяти — ошибка, а не перезагрузка

`Master::load`: образ интерпретатора копируется `bytes.to_vec()` — отказ выделения в Rust = abort. Заменить на
`try_reserve_exact` + понятную ошибку. Пройти путь загрузки модуля (`load`, `kernel.add/swap`, `ModuleHost`)
и `put` на другие крупные выделения.

## 4. Блокировки и очереди

- `i2c_send::QUEUE`, `pcf::TABLE`, журнал `snapshot::JOURNAL`, MQTT `slot_text`/publish: `std::Mutex` →
  `Spin` (шаг — `lock_scan`/`try_lock`, фон — `lock_ceiling`/`lock_wait`) по правилу `specs/fast-cycle`.
  PCF: запись из шага уже только ставит слово, на шину идёт фоновая задача (находка из памяти устарела).
- `io::TO_SCAN` (команды порта → шаг) — без предела: ограничить (64 события), переполнение — ответ `err busy`
  и счётчик.
- Поиск `unwrap/expect/panic!/[i]` в пути шага (`step`, `scan`, `between_steps`, `publish`, функции хоста).

## 5. Образ входов и выходов

`crab-core/src/check/graph.rs::order_blocks`: среди готовых блоков сначала блоки с параметром `pin`
`mode = "in"`, в конце — `mode = "out"` (ключ приоритета `(класс, номер)`). Все входы читаются в начале шага,
выходы пишутся в конце. Снимки `.wat` обновить.

## Риски

- Ложное срабатывание сторожа при долгой работе между шагами — `hold` на каждую известную долгую операцию;
  проверка: заливка модулей при периоде 1 мс без перезагрузки.
- Запись регистров GPIO из прерывания на двух ядрах — только уровни своих выводов, без драйвера.
