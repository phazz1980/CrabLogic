## Сверка 14.11.2026

1. Нехватка памяти: `Master::load` — `try_reserve_exact`; C3 «сеть, затем листы» 5 раз — 5 чистых ошибок
   «allocate memory failed», 0 перезагрузок (было 2 из 5). 10 прогонов из критерия не набрано — 5 + полный бенч.
2. Сторож: C3 — срабатывание через 1,04 с (период 10 мс, предел 1 с), ESP32 — 1,06 с с работающим листом;
   `reset=panic trip=scan:1000`, дамп пишется; 3 подряд → `safe=3`. Полный бенч обеих плат (заливки при 1 мс,
   перезапуски модулей) — ни одного ложного срабатывания. Найдено и исправлено: LLVM сжимал поле-метку в
   RTC-памяти до бита (мусор после включения читался как срабатывание) — доступ `volatile`, так же для
   счётчика загрузок `BOOT_COUNTER`.
3. Безопасные уровни из прерывания: таблица `SAFE` по захватам выводов (хуки `Hal::leased/ended` ядра, тест),
   в прерывании — отвязка от LEDC и уровень. **Не проверено замером на выводе** (нужен мультиметр/логический
   анализатор: уровень держится ~0,2 с до сброса).
4. `Spin` вместо `std::Mutex`: очередь I²C (с уведомлением задачи вместо Condvar), веб-страница (запись
   раскладки в NVS и запуск сервера — вне блокировки: раньше шаг с веб-виджетами ждал запись флеша), журнал,
   PCF. Очередь команд порт → шаг — 64 события, `crab-io` ждёт места. Остались `std::Mutex` в MQTT, UART,
   retain, net (вызовы из шага редкие или через атомики) — следующим шагом при необходимости.
   PCF: запись из шага и так шла через фоновую задачу (находка из памяти устарела).
5. Путь шага: `expect` в чтении АЦП убран; операции шины (I²C, UART, SPI, 1-Wire, импульсы) больше не
   копируют память модуля в `Vec` (SPI — буфер на стеке). Индексация `slots[index]` — индексы из обхода
   `0..len`, оставлена.
6. Порядок блоков: класс по параметру `pin` (`in`/`adc` — вход, `out`/`pwm`/`dac` — выход), тесты; снимки
   модулей не изменились. PCF-блоки — обычные (I²C, не вывод).
7. Справка `help/15-reliability.md`, ссылка из «Сборки», новости.
8. Бенч: ESP32 07:06/07:14/07:39, C3 07:22, строки в `bench/history.md`. **Находка:** ESP32 float в
   интерпретаторе медленнее на 45–55 % (500: 833→1290), logic/timers interp и AOT — без изменений; похоже на
   раскладку (функции float libgcc из флеша) — отдельная задача.

## Найдено позже

9. [x] 14.11.2026, бенч C3 после PCNT: стенд «листы» после сетевых стендов — 5-й лист → `reset=panic`
   (`abort` из std в `Master::start`; в стеке — `Master::start`, `heap_caps_realloc`). Значит, кроме копии
   образа есть другие выделения на пути загрузки (рост `Vec` слотов/ядра, строки ошибок, WAMR), которые у края
   памяти завершают прошивку. Плата перезапускается с дампом, `bad=1`. Сделать: запас памяти перед загрузкой
   (проверка «свободно ≥ образ + N КБ» → ошибка), `try_reserve` для слотов, повтор сценария 10 раз.
   Разбор 14.11.2026: дамп — `std::sys::thread_local::key::unix::fail` (`pthread_setspecific` → ENOMEM, std
   вызывает `abort`): загрузка листа съедала кучу до нуля (WAMR отказывал чисто), а следующее выделение в
   потоке схемы (первая инициализация thread-local std) роняло прошивку. Воспроизводилось 8 из 8 (`bench --only
   net,sheets --quick`). Исправление (`Master::load`): запас `HEAP_RESERVE` = 16 КБ — загрузка не начинается, если
   «свободно < память + копия образа + 12 КБ + запас», а модуль, после которого осталось меньше запаса,
   выгружается с ошибкой «не хватает памяти: …». Проверка: C3 10 прогонов подряд — 0 перезагрузок, листов после
   сети 5; ESP32 3 прогона — листов 7 (раньше на 7-м плата не отвечала), 8-й — чистая ошибка.
10. [x] 14.11.2026: `std::Mutex`/`Condvar` в пути шага — MQTT, Sparkplug, Wi-Fi (`net.rs`), Ethernet, UART, retain,
    АЦП/ШИМ. План:
    - поток схемы не берёт `std::Mutex`/`Condvar` ни в операциях модулей (`devices.rs` → `net`, `mqtt`, `uart`,
      `retain`, АЦП, ШИМ, ЦАП, Sparkplug, Ethernet), ни между шагами (`take_notes` и т. п.);
    - общие с фоновой задачей данные — `Spin`: «потолок» (`lock_scan` / `lock_ceiling`), если участки фоновой задачи
      короткие и без блокирующих вызовов (копия — и вызовы сети уже после отпускания), иначе «попытка»
      (`try_lock`, работа переносится на следующий шаг); данные только потока схемы — `Spin` без соперника;
      флаги и счётчики — атомарные;
    - пробуждение фоновой задачи вместо `Condvar` — уведомление задачи FreeRTOS (не блокирует);
    - журнальные очереди (`NOTES`) — `Spin` «попытка», записи из шага при занятой очереди отбрасываются со счётчиком;
    - retain: запись NVS уходит из шага в фоновую задачу (ограниченная очередь со слиянием по ключу, переполнение —
      счётчик), чтение — только при старте модуля; без выделений памяти в шаге (ключ — в буфере на стеке).
    Проверка: тесты мастера, сборка ESP32/C3, `crablogic bench` обеих плат (сеть, Modbus, retain, UART, cycle_1ms),
    сравнение с 14.11 11:58/12:09.

    `note_queue.rs`, retain — таблица 32 числа + 4 строки, поток `crab-nvs`. Остался `std::Mutex` у `SYSLOOP` (только
    фоновые потоки). Бенч 15:25/15:36 в пределах шума или быстрее. Найдено по ходу: скорость шага на ESP32 зависела
    от раскладки флеш-кэша (первая сборка в 1,7–3 раза медленнее) — быстрые вызовы мастера перенесены в IRAM,
    `CONFIG_ESP_WIFI_RX_IRAM_OPT=n`. Проверено на плате: retain пишет из фона и читается после перезаливки модуля.
