# План: быстрый цикл

## Где задаётся период
- `project.toml`: `[run] period_ms = 10` (1, 2, 5, 10; нет секции — 10). Редактор: «Проект → Настройки», поле
  «Период цикла».
- Генератор пишет его в `module.toml` каждого листа (`period_ms`), как остальные настройки модуля — настройки
  едут с модулями, мастер отдельной командой не настраивается.
- Мастер шагает с наименьшим `period_ms` среди залитых листов (разные периоды по листам — позже, вне задачи).

## Мастер (`firmware/master-rs/src/board/mod.rs`, новый `board/cycle.rs`)
- Было: один поток `crab-runtime` ждал USB с тайм-аутом до конца кванта 10 мс, потом `scan(dt_ms)`; команды
  протокола шли в том же цикле.
- Стало (13–14.11.2026, по замерам), два потока:
  - **Скан** `crab-runtime` (ESP32 — ядро 1, приоритет 20 на обоих чипах). Будит его аппаратный таймер GPTimer
    1 МГц с автоперезагрузкой, прерывание выделено на ядре скана (`board/tick.rs`): тик FreeRTOS обрабатывает
    ядро 0, и с Wi-Fi пробуждение опаздывало (181 опоздание > 50 мкс из 4700 → 5). Без таймера — сетка тиков.
    После шага скан публикует **снимок** (`board/snapshot.rs`, `try_lock` — скан никогда не ждёт): статистику
    модулей, слова выходов, события 0/1 (`ModuleHost::move_events`, без аллокаций), строку цикла. Между шагами
    выполняет только переданные ему команды-действия и шаг заливки.
  - **Ввод-вывод** `crab-io` (ESP32 — ядро 0, обычный приоритет): читает USB, разбирает поток (`Input` под
    `Mutex`: заливка переключает его в режим тела), отвечает на опрос отладки `list`, `info`, `out`, `ev`, `log`
    из снимка и журнала, остальное (заливка, `in`/`param`/`force`, `del`, `swap`, `tick`, `rmax`…) передаёт скану
    очередью. Он же пишет все ответы в порт (`usb::write_line` кладёт строку в очередь).
  - Почему так: команда в потоке скана — «холодный» код из флеша, `list` 0,4–1 мс; с тяжёлым листом это
    сдвигало шаг (пауза 1,6 мс при цели 1,1). Простая общая блокировка не помогла бы: команда держала бы её столько
    же. Ответ из снимка у скана время не берёт.
  - Порядок: ответ на опрос может прийти раньше, чем скан выполнит переданное перед ним действие (например,
    `out` сразу после `force`) — следующий опрос покажет новое; для редактора этого достаточно.
  - Время — `esp_timer_get_time` в мкс; `dt_ms` листу — целые мс с переносом остатка (`src/cycle.rs`, хост-тесты).
  - Период мастера — наименьший `period_ms()` среди запущенных модулей; таймер перезапускается при смене.
  - Во время заливки (стирание и запись флеша) шаг ждёт: разброс допускается (критерий 2 — без заливки).
- Modbus: поток опроса держит блокировку таблиц только на время протокола, сокеты и UART — без неё
  (`Staged`); раньше шаг ждал `accept`/чтение/запись TCP и подключение мастера (до 500 мс).
- Горячий путь шага (`Master::step`, `engine::native`, `dispatch`, `WamrInstance::call`/`call_step`) — в IRAM
  (`#[link_section = ".iram1.*"]`): из флеша шаг упирался в кэш и зависел от раскладки сборки (13.11.2026: на
  том же модуле 88 → 54 мкс в скане, разброс между сборками ушёл). IRAM ESP32 почти занят (свободно ≈12 КБ) —
  туда только код каждого шага.
- Переполнение: если шаг дольше периода — `over += 1`, пропущенные метки отбрасываются (`Ticker::skip`), следующий
  шаг — на следующей метке таймера; пропуски не догоняются. Ожидание метки даёт поработать простою ядра
  (сторож задач). Растущий счёт — в журнал не чаще раза в 10 с.
- Статистика в `list`: строка `cycle period=<мкс> steps= gap=<макс. пауза, мкс> over= late50= late100=`
  (опоздание старта больше 50/100 мкс — для критерия 99 %); `rmax` её сбрасывает.
- Риски: сторож задач на ядре 1 (простой должен успевать — шаг < периода); приоритет относительно
  `esp_timer` и прерываний АЦП/RMT; память: стек нового потока (не хуже на 4 КБ — критерий 6).

## ПК
- `crab-core`: настройка `period_ms` в модели проекта, проверка значения; оценка шага листа
  (`check/cycle.rs`): сумма цены блоков по таблице `crab-core/src/cost.rs` (вид блока → мкс для ESP32 и C3,
  из бенча; неизвестный вид — цена средняя по семейству), предупреждение `step-over-period` при > 70 %.
- `crab-codegen`: `period_ms` в манифест модуля; `crab-sim::mcu::Manifest` его читает.
- `crab-editor`: поле в настройках проекта; в отладке — фактический период, переполнения.
- `crab-cli bench`: стенд `cycle_1ms` (логика на 100 блоков, период 1 мс, Wi-Fi + MQTT, опрос Modbus и `list`),
  отчёт: период, `over`, `late50/100`; таблица цен блоков выводится из уже снятых стендов.
- Справка: `help/05-build.md` (период), `help/06-debug.md` (переполнения), `help/08-errors.md` (новое
  предупреждение), `help/09-news.md`.

## Блокировки между шагом и фоном (14.11.2026)

Замер на ESP32: `std::sync::Mutex` (мьютекс FreeRTOS внутри) — около 5 мкс на блокировку, даже `try_lock`; атомик —
0,2 мкс. Правило для кода, который вызывает шаг:
- состояние, которое шаг только читает или пишет одним словом (Wi-Fi, счётчики MQTT, метрики Sparkplug), — атомики;
- общие структуры (таблицы Modbus, снимок отладки, очередь команд) — `board/spin.rs`: либо «попытка» (скан не ждёт,
  работа переносится на следующий шаг), либо «потолок» (фоновая задача держит блокировку с приоритетом выше скана,
  поэтому на одном ядре скан её всегда застаёт свободной, на двух — ждёт только короткую секцию другого ядра);
- `std::sync::Mutex` — только для редких действий шага (приход сообщения, публикация, настройка).
Фоновые потоки мастера и задачи lwIP и MQTT в ESP-IDF — на ядре 0 (`spawn_background`, `sdkconfig.defaults.esp32`).
