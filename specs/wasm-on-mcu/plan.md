# WASM-модули на микроконтроллере — план

## ABI v3 (было v2; расширение ABI из `wasm-blocks`, числа 32-битные — `specs/numeric-model`)
Типы значений — `i32`/`f32`; строки и данные — указатель+длина в линейной памяти модуля, хост копирует их сам.
Экспорты модуля: `step(dt_ms)`, необязательные `init()`, `on_message(topic_ptr, topic_len, ptr, len)`, `abi_version() -> u32`.
Импорты `crab`: `log`, шина и значения по типам:
- Значения 32-битные: `bool`/`int` — `i32`, `float` — `f32`. Доступ по типу: `input_i/_f(idx)`, `param_i/_f(idx)`, `output_i/_f(idx, v)`, `tag_get_i/_f(id)`, `tag_set_i/_f(id, v)`; слот — 4 байта, тип — взгляд на те же биты. `module.toml`: `abi = 3`, `memory_pages`.
- Теги — обмен с мастером и другими модулями через таблицу тегов хоста.
- Шина: `publish(topic_ptr, topic_len, ptr, len)`, `subscribe(topic_ptr, topic_len)`; хост кладёт в `esp_event`/очередь,
  доставка — вызовом `on_message` между шагами.
- Узкий набор железа (только то, что нужно блокам FBD): `gpio_read/write`, `adc_read`, `pwm_write`, `millis`; позже `math(op, a, b)` (разрешение `math`: 0 sin, 1 cos, 2 tan, 3 pow на `f32`; мастер считает `sinf/cosf/tanf/powf`, чтобы модуль не нёс libm; нужна мастер-прошивка с `P_MATH`).
  Тонкая периферия (RMT, PCNT, MCPWM, DMA) не пробрасывается: остаётся нативным блоком мастера, модуль задаёт уставки.
- Модуль без прав на железо получает только `input/output/tag/publish`; список разрешённых импортов — в манифесте модуля.
Приём сообщений: хост кладёт байты в память модуля через его экспорт `alloc(len) -> ptr`, затем зовёт `on_message`.
Манифест — `module.toml` рядом с `.wasm`: `name`, `abi = 2`, `allow = [...]` (права на `gpio_read`, `gpio_write`, `adc_read`, `pwm_write`, `millis`).
Реализовано в `crab-sim` (`mcu.rs`, тесты `tests/mcu.rs`); железо на ПК — заглушка `StubIo`. Шаг `step` у всех модулей принимает `dt_ms: i32`.
Железо: мастер ставит режим пина (`pinMode`) при первом обращении; в `gpio_read` бит 8 номера пина (`pin | 0x100`) просит подтяжку к питанию; `pwm_write(pin, v)` принимает 0…255 (8 бит, `analogWrite`), модуль сам переводит проценты блока.

Подсчёт: версия ABI проверяется при загрузке (`abi_version`), неизвестный импорт — ошибка с именем.

## Мастер-прошивка (нативный C++, шаблон рядом с `esp32.cpp.tmpl`)
- Core 0: железо и быстрые контуры; Core 1: задачи модулей (по задаче FreeRTOS на модуль).
- Рантайм на модуль с заранее выделенным блоком памяти (против фрагментации); горячая замена: пауза задачи → выгрузка →
  загрузка нового файла → запуск; выходы и состояние нативных блоков не сбрасываются.
- Сторож на каждый модуль (топливо/время шага); при зависании — перезапуск и запись в журнал с причиной.

## Крейты
- `crab-sim`: хост-ABI v3 с заглушками железа (то же, что на плате); бенч сравнения ПК/плата.
- `crab-codegen`: позже второй вывод «схема → WASM» (отдельная спека).
- `crab-build`: сборка мастера и заливка `.wasm` по USB/OTA (файловая система).
- Документы: `Архитектура и план.md` (раздел плагинов/WASM), `help/` — когда появится поведение.

## Риски
- Память ESP32 без PSRAM; скорость интерпретатора (10–30× медленнее нативного) — быстрое остаётся нативным.
- wasm3 почти не развивается; рантайм выбираем по замерам, ABI от рантайма не зависит.
- Расхождение ПК и платы (числа, порядок вызовов) — один общий набор тестовых модулей.

## Замеры прототипа (03.11.2026)
Плата: ESP32 DevKit (без PSRAM), COM10, ядро esp32 3.3.12, Wasm3 0.5.0. Скетч — `proto/mcu_proto/`, модуль — `proto/blink.wat`
(182 байта, импорты `crab.gpio_write`, `crab.millis`, экспорт `step`, `abi_version`). Модуль зашит в прошивку массивом (LittleFS — в задаче 4).
- ОЗУ на модуль (среда + рантайм + стек 2048 слов + модуль): ~5,5 КБ. Свободной кучи в начале ~296 КБ, самый большой блок ~110 КБ.
- Шаг `step` (быстрый путь, проверка времени): 3,74 мкс.
- Горячая замена (выгрузка + загрузка): 628 мкс.
- 1000 замен подряд: свободная куча и самый большой блок не изменились (290744 / 110580) — фрагментации нет.
- Заливка и запуск по USB работают; светодиод на GPIO 2 визуально не проверялся.

**Выбор:** wasm3 — по этим замерам подходит с большим запасом. WAMR и `wasmi` `no_std` не мерили (не нужны, пока wasm3 укладывается);
вернёмся к ним, если понадобятся возможности, которых нет в wasm3 (он почти не развивается). Ограничение: замерен только пустой «мигающий» модуль,
тяжёлые модули (строки, MQTT) дадут другие цифры ОЗУ.

## Замеры мастер-прошивки (03.11.2026)

Прототип: `proto/master/master.ino` + `test.ps1` (заливка по Serial, `put` с CRC32). ESP32 DevKit, wasm3.

- Модуль-«зависака» (`hang.wat`, бесконечный цикл в `step`): сторож убивает задачу через 100 мс и перезапускает (~7 раз/с); соседний `blink` шагает без сбоев (restarts=0).
- Сторож обязан быть на том же ядре, что и модули, с приоритетом выше: `vTaskDelete` задачи с другого ядра вешало плату намертво.
- Заливка модуля по Serial вместе с записью в LittleFS: ≈ 10 мс (`swap_us`), горячая замена — 14–26 мс.
- 1000 горячих замен `blink` при постоянно перезапускаемой «зависаке»: 0 ошибок, 31 с; свободная куча 252900 → 252868 байт (одноразовые 32 байта), самый большой блок 110580 — без изменений, фрагментации нет.

## Большие схемы: замеры (03.11.2026)

Проект из 12-блочных групп (генератор, фронт, счётчик, лимит, арифметика, сравнение, таймер, RS, гистерезис), лист → один модуль. Плата ESP32 DevKit, wasm3; ПК — wasmi (release), `crates/crab-sim/tests/mcu_bench.rs`. Шаг на плате — `tick sheet1 2000 10` по часам ПК (включает обмен по USB, ошибка < 1 мс).

| Блоков | .wasm | Шаг на плате | Шаг на ПК | Куча после загрузки |
|---|---|---|---|---|
| 24 | 1,9 КБ | ≈ 98 мкс | 0,3 мкс | 82 КБ свободно |
| 60 | 4,5 КБ | ≈ 232 мкс | 0,9 мкс | 73 КБ |
| 120 | 8,8 КБ | ≈ 458 мкс | 1,3 мкс | 56 КБ |
| 300 | 22 КБ | не помещается в кучу | 3,2 мкс | — |

- **После перехода на `i32`/`f32` (ABI 3, 04.11.2026):** модули меньше (1,2 / 2,8 / 5,4 КБ для 24 / 60 / 120 блоков), шаг на плате ≈ 87 / 204 / 403 мкс (было 98 / 232 / 458, т. е. ≈ на 12 % быстрее). Куча в этих замерах не сравнима с прежней: на плате стоят ещё модули `counter`/`blink` (свободно 142 / 133 / 117 КБ).
- **Максимум блоков на ESP32 (ABI 3, пустая плата, один модуль-лист):** 600 блоков работают при свободной куче 86 КБ, 720 — при 54 КБ (самый большой кусок 21 КБ), 840 перезагружают плату (не хватает кучи). Итого ≈ 700–750 блоков; прежний предел ≈ 250 (300 не помещались), т. е. примерно втрое больше. Расход ≈ 250 Б кучи на блок, шаг ≈ 3,4 мкс/блок. Узкое место по стеку: при 360+ блоках `step` вызывал 45 кусков подряд, и стек задачи 16 КБ переполнялся (wasm3 не делает хвостовых вызовов); теперь куски вызываются группами по 16 (`PIECES_PER_GROUP` в `wasm.rs`). Лимит `put` мастера 64 КБ упрётся при ≈ 1300 блоков, но раньше упрётся куча.
- **Максимум блоков с Wi-Fi и веб-сервером (ESP32, точка доступа + `WebServer` на :80, сборка мастера с `-DCRAB_WEB`):** Wi-Fi и сервер забирают ≈ 68 КБ кучи (свободно на пустом мастере 270 → 202 КБ). 480 блоков работают (свободно 53 КБ, но самый большой кусок всего 8 КБ), 540 уже не загружаются («no memory»). Итого ≈ 480–520 блоков против ≈ 720 без Wi-Fi. Замер без клиентов и без HTTPS: активные соединения и TLS заберут ещё; режим станции по расходу близок к точке доступа.
- Стоимость ≈ 3,8–4 мкс на блок на плате, ≈ 280 байт кучи на блок; плата примерно в 150–300 раз медленнее ПК. Шаг 10 мс: запас по времени ≈ 2500 блоков, **предел сейчас — ОЗУ** (~250 блоков при пустой плате).
- Найдено и исправлено: (1) `step` одной функцией — wasm3 отказывает («stack height limit»); эмиттер режет `step` на функции по 8 блоков. (2) wasm3 без оптимизации хвостовых вызовов рекурсирует на каждую операцию — стек задачи 6 КБ не хватало, теперь 16 КБ (мастер) и стек `loop` 16 КБ. (3) Временные локали блоков переиспользуются (раньше росли с числом блоков). (4) Память модуля 0 страниц вместо 1 (64 КБ из кучи платы на пустую страницу).
- Дальше для больших схем: стек задачи ужать (10–12 КБ), освобождать .wasm после компиляции, при нехватке — PSRAM-плата или несколько модулей на нескольких листах.
- Мастер на плате: новая версия (pinOnce, подтяжка, стеки). Светодиод GPIO 2 визуально не проверялся.

## wasmi `no_std` против wasm3 на ESP32-C3 (08.11.2026)

Прототип `proto/wasmi-c3/` (Rust nightly, esp-hal 1.2, wasmi 2.0, куча 200 КБ, флеш QIO 80 МГц) грузит те же модули, что мастер:
`blink`, `counter`, `thermostat` (17 блоков), `selftest_logic*` (42 и 107 блоков). Хост-функции — заглушки, без железа.
Для сравнения на той же C3 (COM5) стоял мастер wasm3 (сборка под `selftest_logic3`): `put` + `list`/`stats`.

| модуль (.wasm) | куча wasmi* | куча wasm3** | шаг wasmi | шаг wasm3 | замена wasmi | замена wasm3 |
|---|---|---|---|---|---|---|
| blink (209 Б) | 7,6 КБ | 14,3 КБ | 12,8 мкс | 5 мкс | 6,3 мс | 2,1 мс |
| counter (646 Б) | 16,3 КБ (из них 4 КБ память) | 20,0 КБ (4 КБ) | 52,7 мкс | 23 мкс | — | 3,4 мс |
| thermostat 17 (1,3 КБ) | 15,8 КБ | 21,1 КБ | 114 мкс | — (АЦП) | 21 мс | 5,4 мс |
| selftest 42 (3,6 КБ) | 29 КБ + память | 35,5 КБ (3,3 КБ) | 980 мкс | 800 мкс (с UART) | — | 11,5 мс |
| selftest 107 (8,9 КБ) | 55 КБ + память | 67,6 КБ (8,3 КБ) | 2225 мкс | 1761 мкс (с UART) | 69 мс | 24 мс |

\* wasmi: модуль + Store + экземпляр + скомпилированный код после первого шага, без стека задачи; линейная память отдельно.
\** wasm3: падение свободной кучи после `put`, включая задачу FreeRTOS со стеком 5 КБ и память модуля.

Выводы:
- **ОЗУ — сопоставимо**, wasmi даже на 5–7 КБ меньше на модуль (но у мастера wasmi тоже будет задача со стеком). Код wasmi ≈ 6× размера .wasm (wasm3 ≈ 3,7×).
- **Шаг — wasmi медленнее**: в 2–2,5 раза на маленьких модулях (накладные расходы вызова ≈ 12 мкс против 5) и ≈ в 1,3 раза на больших.
- **Загрузка/замена — wasmi в 3 раза медленнее** (валидация + перевод в свой байткод); на 100+ блоков ≈ 70 мс. Lazy-режимы снижают загрузку лишь на ~25 %.
- Линейная память: wasm3 берёт размер из `crab.mem` (3–8 КБ), wasmi — страницу 64 КБ, если модуль не объявит `(pagesize 1)` (предложение custom-page-sizes, `counter_p1`: 4 КБ вместо 64). Для wasmi эмиттер должен писать память так.
- **Engine держит код удалённых модулей**, пока жив сам engine (+5…43 КБ на загрузку): горячая замена с общим engine утекает и падает на 2-й замене. Нужен свой `Engine` на слот: тогда 1000 замен без дрейфа кучи.
- Fuel: прерывание бесконечного цикла и продолжение (`call_resumable` → `OutOfFuel` → `resume`) работают; ≈ 0,36 мкс на единицу fuel; учёт fuel стоит 1–5 %.
- Подводные камни сборки: на RV32IMC нет атомиков — nightly + `build-std` + target с `atomic-cas` + свои `__sync_*` (запрет прерываний). У wasmi 2.0 **обязательно** `portable-dispatch` при `default-features = false`: иначе обработчики вызывают друг друга без хвостовых вызовов и стек переполняется на первом длинном цикле (и шаг вдвое медленнее). Прошивка прототипа ≈ 1,2 МБ (wasmi + wasmparser с валидацией).

## WAMR на ESP32-C3 (08.11.2026, этап 0 `specs/wasm-kernel`)

Прототип `proto/wamr-c3/` (WAMR 2.4.5, ядро Arduino esp32 3.3.12 = ESP-IDF 5.x, флеш QIO 80 МГц, плата C3 на COM5)
грузит те же 5 модулей. Режимы: классический интерпретатор (`interp`); AOT с XIP (`aot`): образ из флеша выполняется
на месте, `wamrc --xip`, проверка границ включена; то же без проверки границ (`aotnb`). Хост-функции — заглушки.
Куча — модуль + экземпляр (вместе с линейной памятью из `crab.mem` и стеком wasm 4 КБ) + exec env.
Рантайм работает в одной задаче (pthread, стек 32 КБ) на все модули.

| модуль (.wasm → .aot) | куча interp | куча aot | куча aotnb | куча wasm3 | шаг interp | шаг aot | шаг aotnb | шаг wasm3 | замена interp | замена aot | замена wasm3 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| blink (209 Б → 840) | 8,0 КБ | 12,2 КБ | 7,8 КБ | 14,3 КБ | 12,7 мкс | 8,5 мкс | 8,4 мкс | 5 мкс | 1,3 мс | 1,2 мс | 2,1 мс |
| counter (646 Б → 2,5 КБ) | 14,6 КБ | 17,6 КБ | 13,2 КБ | 20,0 КБ | 51 мкс | 35 мкс | 35 мкс | 23 мкс | 2,2 мс | 1,4 мс | 3,4 мс |
| thermostat 17 (1,3 → 3,3 КБ) | 12,3 КБ | 14,1 КБ | 9,7 КБ | 21,1 КБ | 98 мкс | 41 мкс | 41 мкс | — | 3,4 мс | 1,8 мс | 5,4 мс |
| selftest 42 (3,6 → 21,7 КБ) | 22,8 КБ | 21,1 КБ | 16,7 КБ | 35,5 КБ | 655 мкс | 906 мкс | 881 мкс | 800 мкс* | 7,0 мс | 3,1 мс | 11,5 мс |
| selftest 107 (8,9 → 53,4 КБ) | 44,6 КБ | 34,5 КБ | 30,1 КБ | 67,6 КБ | 1818 мкс | 2577 мкс | 2448 мкс | 1761 мкс* | 15,8 мс | 6,2 мс | 24 мс |

\* wasm3 — с настоящим UART. Замена: загрузка + экземпляр + init + шаг + выгрузка; 1000 замен thermostat17 и
selftest107 — дрейф кучи 0 в обоих режимах. Все 5 модулей сразу: interp 102 КБ, aot 100 КБ, aotnb 78 КБ
(wasm3 ≈ 158 КБ по сумме строк). Сам рантайм после инициализации — 180 Б кучи.

Выводы:
- **XIP на C3 работает**, но с хитростью: загрузчик AOT в indirect-режиме ставит указатели функций в адреса шины
  данных (DROM 0x3C…), а выполнять надо через шину команд (0x42… = DROM + 0x0600_0000, у C3 общая MMU).
  `shim_aot_to_ibus` переводит таблицу до создания экземпляра. В ОЗУ остаются только данные модуля.
- **ОЗУ — WAMR заметно лучше wasm3**: на больших листах aot ≈ 0,5×, interp ≈ 0,65× от wasm3 (но у wasm3 в цифре
  ещё задача со стеком 5 КБ на модуль, у WAMR одна задача на всех). AOT с проверкой границ держит на модуль
  постоянные +4,4 КБ при загрузке (причину не выясняли).
- **Шаг — WAMR медленнее wasm3**: накладные расходы вызова `step` ≈ 8 мкс (aot) и 12 мкс (interp) против 5.
  **AOT из флеша упирается в кэш флеша** (16 КБ): лист FBD — длинный линейный код, каждый шаг заново читается
  из флеша, время ≈ размер кода / 20 Б/мкс (21,7 КБ → 0,9 мс; 53 КБ → 2,6 мс). Поэтому на больших листах AOT
  медленнее интерпретатора WAMR (его код маленький и сидит в кэше, байткод в ОЗУ). Ускорить можно копией кода
  горячего модуля в IRAM (на ESP-IDF — `MALLOC_CAP_EXEC` при выключенном memprot), но тогда ОЗУ ≈ 6× .wasm.
- **Проверка границ дешёвая**: шаг +0…5 %, код +6…30 %. Отключать её не стоит (безопасность важнее).
- **Загрузка и замена — WAMR в 2–4 раза быстрее wasm3**, aot быстрее всего (6 мс на 107 блоков).
- **Флеш**: AOT ≈ 4× .wasm на маленьких модулях и ≈ 6× на больших (≈ 500 Б на блок против ≈ 83 у .wasm).
  Нынешний `crabmod` (16 областей по 68 КБ, модуль ≤ 64 КБ) вмещает лист ≈ 130 блоков в AOT против ≈ 700 в .wasm.
  Для AOT нужно: приложение 1,5 МБ, `crabmod` ≈ 2,4 МБ и области переменной длины (по секторам 4 КБ), а не
  фиксированные 68 КБ. Тогда с запасом под горячую замену на плате ≈ 1,2 МБ AOT ≈ 2400 блоков.
- **Быстрый интерпретатор WAMR (fast-interp) портит кучу** на thermostat17 (хвост блока кучи затирается во время
  шагов; не стек и не линейная память — проверено). Берём классический: на маленьких модулях он не медленнее fast
  (12,7/51 мкс против 12,0/52,6), на больших fast не мерили. Если понадобится fast — сначала найти ошибку.
- Подводные камни сборки: WAMR под ESP-IDF вызывает `pthread_self` — рантайм только из pthread; без заданной границы
  стека (`wasm_runtime_set_native_stack_boundary`) каждый вызов сканирует стек FreeRTOS (≈ 900 мкс на шаг);
  загрузчик интерпретатора правит байткод — `.wasm` копируется в ОЗУ; модулю с `(memory 0)` память не выделяем.
- Прошивка прототипа ≈ 415 КБ без образов модулей (Arduino + WAMR interp + AOT), против ≈ 1,2 МБ у wasmi.
- `wamrc` 2.4.5 (LLVM): 20 МБ в архиве, 48 МБ распакованный.

**Вывод по Rust-мастеру: да, с поправкой.** WAMR на C3 под ESP-IDF работает и решает главную задачу — ОЗУ:
на больших листах вдвое меньше wasm3, утечек при замене нет, замена в 2–4 раза быстрее. Цена — шаг: на мелких
модулях в 1,5–2,5 раза медленнее wasm3, на больших AOT из флеша упирается в кэш (2,6 мс на 107 блоков; для цикла
ПЛК 10–100 мс это допустимо). Поправка к плану: на плате два режима WAMR по модулю — AOT с XIP по умолчанию (меньше
ОЗУ, быстрая замена) и классический интерпретатор для листов, которым важнее скорость шага; `crabmod` переделать
под AOT (области переменной длины, ≈ 2,4 МБ).

### Ускорение шага AOT (08.11.2026)

Стенд тот же (`sketch/bench.cpp`, колонка `calls` — вызовов хоста на шаг). Микромодули `wat/calls7.wat`,
`calls1.wat`, `loop100.wat`: 100 вызовов `crab.text` (7 аргументов) / `crab.tag_get_i` (1 аргумент) / цикл из
100 итераций без вызовов.

**Цена вызова хоста** (на вызов): aot — 2,3 мкс (1 аргумент) и 4,6 мкс (7); interp — 2,8 и 6,8 мкс. Цикл без
вызовов: aot 0,11 мкс на итерацию, interp 3,1. selftest107 делает 158 вызовов на шаг, selftest42 — 61. Причина
в AOT: wamrc не знает сигнатуры импорта и вызывает его через `aot_invoke_native` — аргументы раскладываются
побайтно в массив, ≈ 200 Б кода на место вызова с 7 аргументами; это ≈ ¾ кода листа.

**1. Флаги wamrc** — без выигрыша. Размер .aot selftest107/selftest42, Б: `--opt-level=3` 53428/21706, 2 —
53424/21674, 1 — 53416/22490, 0 — 59812/24482; без LTO 53428/21646; O2 без LTO 53368/21594; без jump tables
53428/21706. `--size-level` — это модель кода (3 = small по умолчанию), `-Os` у wamrc нет.

**2. Общая функция вместо места вызова** (`tools/wrap_calls.py`: обёртка-функция wasm на каждый импорт
`crab.text`/`crab.uart`, вызовы идут через неё; вариант `wi` — через `call_indirect` по таблице). LLVM обёртку не
встраивает, место вызова сжимается до обычного `call`.

| модуль | .aot, Б | шаг aot | шаг aotnb | шаг interp |
|---|---|---|---|---|
| selftest107 | 53428 | 2561 мкс | 2470 мкс | 1818 мкс |
| selftest107 + обёртки | 19996 | 1318 мкс | 1079 мкс | 2287 мкс |
| selftest107 + `call_indirect` | 71380 | 2095 мкс | 1942 мкс | 2456 мкс |
| selftest42 | 21706 | 1008 мкс | 861 мкс | 661 мкс |
| selftest42 + обёртки | 8966 | 345 мкс | 334 мкс | 843 мкс |
| selftest42 + `call_indirect` | 29086 | 523 мкс | 491 мкс | 866 мкс |

Куча не меняется (selftest107 aot 34,5 КБ в обоих случаях). Обёртки дают AOT ×2–3 по скорости и ÷2,5 по коду
(≈ 190 Б на блок вместо 500), и selftest107 в AOT (1,1–1,3 мс) становится быстрее wasm3 (1,76) и interp. Interp от
обёрток медленнее на 25–30 % (лишний вызов wasm), поэтому обёртки — только при сборке под AOT.
`call_indirect` раздувает код — не годится.

**3. Raw-нативы** (`-DCRAB_RAW=1`: те же хост-функции через `wasm_runtime_register_natives_raw`, аргументы
одним массивом `uint64_t`): вызов с 7 аргументами 4,6 → 3,9 мкс, с 1 аргументом без изменений; шаг selftest107
aot 2561 → 2411 мкс, с обёртками 1318 → 1182, interp 1818 → 1694; selftest42 aot 1008 → 932, с обёртками
345 → 300. Выигрыш 6–12 %, код .aot тот же. Брать вместе с обёртками (на хосте дешёвая правка).

Не проверено: прямой нативный вызов без `aot_invoke_native` (wamrc знает сигнатуры через `--native-lib`) —
это работает только с wamrc под Linux (dlopen) или своей сборкой wamrc; ожидаемо ещё быстрее, отложено.

**Вывод по ускорению:** флаги не помогают; главное — места вызова хоста. Эмиттеру при сборке под AOT выводить
вызовы импортов через обёртку-функцию на импорт (2–3× по шагу, ÷2,5 по флешу — снимает и часть проблемы
`crabmod`), хосту регистрировать raw-нативы (ещё ≈ 10 %). «Общая функция на тип блока» сверх этого не мерили:
обёртки уже убирают главный источник кода.
