# Драйверы железа в WASM поверх шин мастера

Продолжение `specs/drivers/` (нативная часть `native.cpp`) и `specs/wasm-blocks/` (`block.wasm`) для полного перехода
на Rust. Решение пользователя 11.11.2026: свой датчик или шина пишется как WASM-блок на любом языке, а к железу он
ходит через общие функции мастера (GPIO, I²C, SPI, UART, 1-Wire). Мастер не пересобирается, компилятор у
пользователя не нужен (нужен только автору блока).

## Цель

Блок для нового датчика (например, BMP280 по I²C или HX711 на двух выводах) пишется как `block.wasm` рядом с
`block.toml` и заливается на плату модулем, без прошивки мастера. Распространённые драйверы (DS18B20, DHT22, Modbus,
UART, PCF8574) остаются встроенными в мастер. `native.cpp`, шаблоны C++ и arduino-cli для новых блоков не нужны.

## Сценарии

1. Автор пишет на Rust (или C, Zig) драйвер BMP280: в `init` читает калибровку по I²C, в `step` запускает измерение
   и через шаг читает результат. Кладёт `block.wasm` в папку блока — блок виден в библиотеке.
2. Пользователь ставит блок на схему, задаёт выводы SDA/SCL и адрес. `check` ловит конфликт выводов и адресов
   с другими блоками, как у встроенных.
3. Схема собирается в модуль (`gen-wasm`), код драйвера входит в модуль. Мастер даёт модулю доступ только к выводам
   и адресам, объявленным в `block.toml`.
4. В редакторе (симуляция) драйвер работает с поддельной шиной: выходы берутся из значений `sim` в `block.toml`
   или из ответов устройства, записанных автором.
5. Драйвер с ошибкой (нет ответа устройства, зависание) не роняет мастер: ошибка шины возвращается кодом,
   зависание обрывается лимитом шага, в журнале — блок и причина.

## Критерии готовности (проверяемые)

- Набор функций хоста для шин описан одной таблицей (имя, аргументы, коды ошибок) в справке; одинаков для C3 и ESP32.
- Пример драйвера на Rust и на C в `examples/` (I²C-датчик); собирается в модуль, проходит `check` и тест в `crab-sim`
  с поддельной шиной.
- Мастер (Rust) собирается для C3 и ESP32 с функциями шин; доступ к чужому выводу или адресу отклоняется (тест на ПК).
- Встроенные блоки не меняются; старые `native.cpp` продолжают работать до отдельного решения о переносе.
- Справка: страница про драйверы, редактор блока, `docs.md` примера. На железе — когда будет датчик (иначе
  «не проверено на железе»).

## Вне задачи

- Протоколы с точным временем на уровне микросекунд из WASM (DHT22, WS2812, ИК): они остаются функциями мастера.
- Прерывания и DMA для драйверов; сеть из драйвера (сеть — у блоков сети).
- Перенос существующих `native.cpp` и мастер-помощника Arduino-библиотек (`specs/native-wizard/`).

## Вопросы к пользователю (ответы 11.11.2026: 1 да, 2 да, 3 да, 4 а, 5 да)

1. **Какие шины первыми.** Предлагаю: GPIO (вход/выход, уровень), I²C, UART (уже есть в модулях), затем SPI,
   затем 1-Wire (сброс, байты). Согласны с порядком?
2. **Долгие операции.** Вызов шины синхронный и короткий (одна транзакция I²C — доли мс). Долгое ожидание
   (преобразование DS18B20 ~750 мс) драйвер делает сам по шагам: «запустил — через N шагов прочитал». Блокирующих
   `delay` в драйвере нет. Так подходит?
3. **Права.** Драйвер видит только выводы и адреса из своих параметров (`type = "pin"`, `i2c_address`), мастер
   проверяет каждый вызов. Подходит, или нужен «полный доступ» с предупреждением?
4. **Симуляция.** Достаточно значений `sim` из `block.toml` (выход = число), или нужна поддельная шина, где автор
   задаёт ответы устройства по регистрам (точнее, но сложнее)?
5. **Судьба `native.cpp`.** Он требует arduino-cli и C++-мастер. Предлагаю: заморозить (новое не добавлять),
   встроенные драйверы перенести в Rust-мастер, а пользовательские `native.cpp` переписать в WASM по мере надобности.
   Согласны?

## Решено (11.11.2026)

1. Порядок: GPIO, I²C, UART → SPI → 1-Wire.
2. Вызовы шины короткие, без блокирующего `delay`; долгие ожидания драйвер делает по шагам.
3. Драйвер видит только свои выводы и адреса; мастер проверяет каждый вызов.
4. Симуляция: значения `sim` из `block.toml` (поддельной шины нет).
5. `native.cpp` заморожен: новое не добавляем, встроенные драйверы переносим в Rust-мастер, свои `native.cpp`
   переписываются в WASM по мере надобности.
